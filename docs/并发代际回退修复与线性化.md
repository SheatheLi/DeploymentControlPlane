# 并发代际回退：实际 SQLite 事务协议修复

## 原始缺陷
旧实现 `change_generation` 先 SELECT 当前 epoch，后做无条件 UPSERT。两个控制器都可以读到 1，然后高代际 3 先成功提交、低代际 2 后提交，把已经持久生效的 3 回退为 2。这会突破控制面恢复与租约 fencing 依赖的单调性不变量。

## 机制级变更
`src/effect_outbox.py` 改为 `INSERT...ON CONFLICT DO UPDATE SET generation=excluded.generation WHERE excluded.generation>workflow_epoch.generation`。检查与写入在**同一个数据库原子写事务**中发生，这条 SQL 就是线性化点。失效 epoch 被明确拒绝，而不是只靠调用端时机。

## 真实负对照
`benchmarks/baselines/effect_outbox_before_fencing.py` 保存旧代码。`benchmarks/generation_fence_race.py` 用两个真实 SQLite 连接强制：旧版两个 SELECT 都看到 1，让 epoch 3 先写、epoch 2 后写，最终错误变成 2；修复版强制 epoch 3 的原子 UPSERT 先提交，较旧 epoch 2 的条件 UPSERT 返回 stale，最终为 3。另做 16 线程并发提交 2..41，最终保证 41，且过期 epoch 的原有 effect 不能再被领取。

这是**局部真实性、明确不变量、强负对照、原子修复**的一条工程事实，胜过“多个 Worker 能恢复”这种模糊结果。但它仅对同一个 SQLite 文件/数据库的协调域成立，不等于分布式双主、多存储 fencing，也不是任何 Temporal/Kubernetes 的上游修复。
